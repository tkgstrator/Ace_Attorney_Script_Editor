# 逆転裁判特有のカタカナ表記

逆転裁判のシナリオは、本来なら漢字・ひらがなで書く語をあえてカタカナで書く場面が非常に多い
（例: 事実→ジジツ、俺→オレ）。LLM にシナリオを書かせるとき、この表記を再現できるかどうかで
「それっぽさ」が大きく変わるため、実データから傾向を調べてまとめた。

## 調査方法

「逆転裁判 蘇る逆転」（GS1・DS リメイク版）・「逆転裁判2」（GS2・DS版）・「逆転裁判3」（GS3・DS版）の
`mes_all.bin`（台本）を `tools/rom/script_dump.py` で展開し、`[...]` の制御コードを取り除いた地の文から
カタカナ連続 2 文字以上のトークンを数え、対応する漢字表記の出現数と突き合わせた。

- GS2・GS3 は `assets/extracted/font/{A2GJ,YG3J}/mapping.tsv` + `tools/rom/font_fixes.{A2GJ,YG3J}.tsv`
  を使って展開した（`assets/extracted/font/mapping.tsv` は GS1 専用なので、これを GS2/GS3 にそのまま
  使うと漢字が別の字になって化ける。ひらがな・カタカナの文字コードは全作品共通なので、カタカナの集計
  自体はどちらの表でも正しい）。
- GS3 は台本の命令テーブルが一部 GS1/GS2 と異なり、86 項目中 14 項目でデコードに失敗した
  （命令の引数の数が合わずズレる）。集計はデコードできた 72 項目分のみ。
- 数値は「地の文にそのトークンが何回出たか」の単純カウント。文脈（誰のセリフか・強調かどうか）は
  見ていないので、比率はあくまで目安。

## ルール4（注意）: カタカナ化「されない」語

直感に反するが、法廷パートの中心用語のうち何語かは、地の文では**ほぼ常に漢字**で書かれる。
LLM が「証拠→ショウコ」「証言→ショウゲン」のように書きたがったら、それは誤り（このゲーム独特の
「わざと崩す」対象には入っていない）。

## 別パターン1: 語幹だけカタカナ＋送り仮名はひらがな

形容詞の語幹だけカタカナにして、活用語尾（い・く・かった等）はひらがなのままにする書き方が
3作品とも安定して出る。

| 例 | GS1 | GS2 | GS3 |
|---|---|---|---|
| コワい／コワく／コワかった | 32 | 47 | 48 |
| ヒドい／ヒドく | 36 | 53 | 39 |
| スゴい／スゴく | 19 | 39 | 44 |

## 別パターン2: 語のカタカナ化ではないもの（参考・区別すること）

- **語尾の口癖**: 「〜ッス」（〜です の砕けた語尾）が3作品とも突出して多い（1015 / 1018 / 1546 件）。
  これは単語の言い換えではなくキャラクターの喋り方なので、上の対応表とは別に「このキャラは語尾が
  ッスになる」という設定として扱う。
- **役職・呼び名の名札**: `assets/extracted/tables/names.json` を見ると、名札そのものがカタカナ化
  された役職名になっている例がある。お巡りさん→**オマワリ**、裁判官→**サイバンカン**、観衆→
  **カンシュウ**、看守→**カンシュ**、先生→**センセイ**、課長→**カチョー**、監督→**カントク**。
  モブキャラの名前を考えるときの参考になる。

## LLM に書かせる／機械的に置換する、どちらが良いか

- **LLM に直接カタカナで書かせる**場合、ルール1の語（ほぼ確定）はそのまま使わせてよいが、
  ルール2・3（確率的）とルール4（カタカナ化しない）を混同しやすい。プロンプトに埋め込むなら
  「ルール1の語は必ずカタカナ」「証拠・証言・尋問・真実・質問は必ず漢字」の2点だけ強く指示し、
  ルール2・3は「迷ったら漢字のままでよい」くらいに緩めておくのが安全。
- **後処理で機械的に置換する**場合は、ルール1の語（俺→オレ、矛盾→ムジュン 等）だけを対象にすれば
  誤爆が少ない。ルール2・3は文脈依存（同じ「コト」でも軽い相槌なら漢字のままの方が自然な場合がある）
  ので、そのまま全置換すると不自然になりやすい（例: 「大事なことがある」→「大事なコトがある」は
  文脈次第で不自然）。ルール4の語は置換対象から必ず除外する。
- どちらの方式でも、**この一覧をプロンプトまたは置換テーブルの元データとして直接使い回せる**ように、
  表はそのまま「通常表記 → カタカナ表記」のペアの並びにしてある。

## 利用できる漢字（DS 版フォントの制約）

`apps/player` はデフォルトでは同梱の PixelMplus12/10（一般的な TTF、常用漢字含め問題なく描ける）で
描画するが、DS 版の見た目そのままにしたい場合は ROM から取り出したドット絵フォント
（`assets/extracted/font/ds-font.json`、README の「DS 版から取り出したフォント」参照）を使う。
このフォントで**そのまま**描ける漢字は ROM に実在した字だけで、無制限ではない。

- 3作品（GS1・GS2・GS3）の ROM にある漢字を重複除いて合計すると 1484 字（常用漢字 2136 字より
  だいぶ少ない）。実際の字は [使える漢字の一覧](available-kanji.txt) に一覧がある
  （`python3 tools/rom/available_kanji.py` で再生成できる。`assets/` は `.gitignore` 対象で
  ROM を自分で吸い出したときしか存在しないが、このテキストファイル自体は「ROM のどの字が使えるか」
  という事実の一覧であって字形（ドット絵）そのものではないので、リポジトリに含めてよい）

ROM にない漢字は `tools/rom/compose.py` で部品から組み立てられるが（`font_extra.draft.txt`
に下書きが出る）、目で見て直す手間がかかる。

**重要な注意**: 上のルール1〜3の対応表にある語は、あくまで「演出としてカタカナが好まれる語」で
あって、「フォントに漢字が無いからカタカナにしている」のではない。実際に `available-kanji.txt` と
突き合わせると、ルール1（ほぼ決め打ちでカタカナ）の語のうち字形が本当に**存在しない**のは
俺・僕・儂・鍵・嫌・綺麗・完璧（の「璧」）・駄目/無駄（の「駄」）くらいで、矛盾・無理・簡単・謎・
言葉・訳・君・貴様・残念・偽物/本物 は漢字の字形自体はフォントにある（単に演出上カタカナが選ばれて
いるだけ）。つまり「対応表に載っている＝フォントに無い」ではないので、フォントの制約を機械的に
確認したいときはこの表を目視で照合するのではなく、下の `--check-font` を使うこと。

### `bun run check --check-font` でフォント側を機械的に確認する

LLM に「この漢字は使うな」と直接指示しても守られるとは限らないため、書かせたあとに
`bun run check --check-font <シナリオ.yaml>` を走らせて機械的に検証する。

- YAML 中のすべての文字列（台詞・タイトル・証拠品名・説明文など）を 1 文字ずつ調べ、
  `available-kanji.txt`（＋ひらがな・カタカナ・記号）に無い文字をエラーとして報告する。
- 上のルール1〜3の対応表（`packages/script/src/katakana-style.json`）と突き合わせて、
  該当する語があれば言い換え候補をメッセージに添える（例:
  `文字「駄」は DS 版フォントにありません。言い換え候補: 無駄→ムダ / 駄目→ダメ`）。
  ルール4（証拠・証言・尋問・真実・質問・私）は候補として使わない。
- 候補が無い文字は「言い換えてください（対応する候補なし）」とだけ出す。
  **このツールは書き換えまではしない**（`--fix` のような自動置換は無い）。実際にどう言い換えるかは
  LLM か人間が診断結果を見て判断する。
- 既定（フラグ無し）ではこのチェックは走らない。PixelMplus フォールバックで表示する分には
  関係ない制約なので、DS 版フォントで表示する章だけ付ければよい。
